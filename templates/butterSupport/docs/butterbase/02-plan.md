# Plan — Butterbase Support Recipe

Generated by `journey-plan`. Updated as each section is confirmed.

## Decisions locked

- **Hackathon mode:** false (full journey, no scope-cut).
- **Substrate link:** this app will link to substrate owner `249d87fa-a4a9-4456-b647-f05221472bc8` (same as `butterbase-crm`). Customer/company identity is read from the shared substrate entity graph — no local people/companies tables.
- **Inbound channel (v1):** in-app widget only, but the inbound representation is channel-agnostic (email/etc. plug in later as new adapters).
- **Escalation channel (v1):** both Slack and Gmail/email, founder picks per workspace.
- **Frontend stack:** Vite + React. Two artifacts:
  - **Founder console** — full SPA, the triage inbox, skill editor, autonomy dial, escalation config.
  - **Customer widget** — small embeddable bundle (separate Vite entry), drops into the customer's app.
- **Per-ticket agent runtime:** Durable Object per ticket (`SupportTicketDO`, instance id = ticket_id). Holds live agent thread state in memory + transactional KV, WebSocket-streams diagnosis tokens to the founder UI. Postgres holds the inbox list + persisted final-state rows for history/queries.
- **Capability naming for first safe actions:** `support.resend_verification_email`, `support.retry_failed_webhook`, `support.flag_as_bug`, `support.apply_account_credit` (last one always-require-approval; first three default-approval-required, escalatable to auto via the autonomy dial).
- **Default sales posture in shipped skill:** help-first, mention upgrades only on clear fit or explicit ask, never push after one mention.

## Distribution & knowledge depth

This recipe is OSS / clonable (`publish_as_template: yes`). Any Butterbase customer (and non-Butterbase customer who wants the substrate) clones the recipe into their own account and stands up support in minutes. Each clone is a fully independent Butterbase app with its own db, frontend, widget secret. Substrate is the only shared surface.

### Two depths, one recipe

The same agent loop runs at two depths, gated by what data is available — NOT two separate builds.

| Tier | What the agent reads | What the agent does | Audience |
|---|---|---|---|
| **Commodity (front door)** | Recipe-local RAG over scraped URLs + uploaded docs | Drafts an answer grounded in the docs; founder approves/edits/sends; escalates if uncertain | Anyone day-one, including non-Butterbase companies. ~60s magic moment after paste-URL. |
| **Deep (headline)** | Commodity sources + substrate (person/company entities, source_artifacts projected by the customer's main app, decisions, commitments, learnings) | Same as commodity + diagnoses against real product data + proposes governed actions via `support.*` capabilities | Customers whose main product app projects signals into substrate. Native Butterbase apps get the deepest tier by default; non-natives deepen as they project more. |

Implementation: **one** agent in the `SupportTicketDO` with **two** tool branches: `search_docs` (RAG, always available) and `read_substrate` (entities + memory + source artifacts, available iff substrate has signal). Depth is a runtime property of what the tools find, not a config switch.

### Front-door onboarding (commodity tier, ≤60 seconds)

1. Clone the recipe → Butterbase provisions a new app (frontend + functions + DO + db).
2. First user signs in via magic link → post-auth hook bootstraps them as `owner` + adds their email to `app_allowlist`.
3. Setup wizard step 1: **"Paste your help-center / docs URL."** Triggers `ingest-docs` which crawls and pipes into `manage_rag_content` (a recipe-local RAG collection).
4. Setup wizard step 2: paste the widget snippet into your product. Wizard reveals the widget HMAC secret ONCE.
5. Working agent. Tickets arrive in the inbox. Founder approves drafted replies.

### Deep-tier onboarding (incremental, when ready)

1. Link the cloned recipe's substrate to the customer's substrate user (so it sees their entity graph + projected product signals). One MCP/SDK call.
2. (For non-native customers) document what signals to project and how — adapter recipe / docs.
3. Enable `support.*` action capabilities in the founder console. For each enabled capability, the console shows the adapter snippet the customer's main product app must register as the substrate outbox target.
4. As substrate populates, the agent's diagnoses get richer. Same recipe, no migration.

### Structural safety floor (non-editable, ours)

These constraints are enforced by code in the recipe — **the customer's `support_skill` cannot disable them**:

1. **Propose-policy-execute discipline.** All side-effect actions go through `ctx.substrate.propose`; agent code can never call action endpoints directly.
2. **Always-require-approval capabilities never auto-execute.** `support.apply_account_credit` (and any future capability marked `requires_human_approval: true` in its declaration) cannot be flipped to auto by yolo_mode or by an `autonomy_settings` row. Enforced at propose-time inside the recipe code.
3. **Audience-scoped disclosure.** Every outbound message (anything that leaves the recipe toward the end-customer — widget reply, or escalation that fans out to the end-customer) passes through a disclosure filter that has read access ONLY to a whitelisted set of substrate fields (the customer's own entity attributes + their own ticket history). Internal-only fields (other customers' data, MRR, internally-tagged commitments, founder notes) are structurally unreadable on the outbound code path. If the agent tries to quote one, the filter strips it and logs a violation. Implemented as a separate substrate access scope used only on the outbound code path.
4. **Always-escalate path.** No code path can disable the escalation capability. If the agent runs out of options and can't draft a confident reply, it escalates — even if the customer disabled the escalation target. (In that case it logs an `unescalated_block` and surfaces it in the inbox as red.)

The customer's `support_skill` lives in the layer ABOVE this floor — it shapes tone, posture, when to mention upgrades, how formal to be. It cannot reach below.

## Tables

**Tenancy model:** single-tenant per cloned app deployment. The Butterbase app is linked to ONE substrate owner (the founder). All authenticated end-users of THIS app are the founder's team. There is NO `workspace_id` column on any table — the app instance itself IS the tenant boundary.

### Tenancy + bootstrap
- **`memberships`** — `id uuid pk`, `user_id uuid` (Butterbase end-user id), `role text` (`owner|admin|member`) default `'member'`, `invited_email text` (snapshot of the email used at sign-in, for audit), `added_by uuid` (nullable for the bootstrap row), `added_at timestamptz` default `now()`. Unique on `user_id`. **Created post-auth** by the hook after looking up the user's email against `app_allowlist`. The first authenticated user post-deploy is auto-inserted as `role='owner'` (and their email auto-added to `app_allowlist`) by the same hook.
- **`app_allowlist`** — `id uuid pk`, `entry_type text` (`email`|`domain`), `value text`, `active bool` default `true`, `default_role text` (`owner|admin|member`) default `'member'` (used by the post-auth hook when creating the membership row), `note text`, `created_by uuid` (nullable for bootstrap), `created_at`, `updated_at`. Unique on `(entry_type, value)`. **Pre-auth gate** — gates who can succeed past the post-auth hook. Founders pre-add employee emails here BEFORE the employee signs in (the employee has no user_id yet, only an email). First successful sign-in self-bootstraps the founder's email into this table.

### Inbox (channel-agnostic)

Indexes: `(status, last_message_at desc)`, `(customer_substrate_id, opened_at desc)`.

Index: `(ticket_id, created_at)`.

Indexes: `(created_at desc)`, `(entity_type, entity_id, created_at desc)`.

Unique `(signal_kind, signal_key)`. v1 detection = cron sweep.

### Integration plumbing
- **`team_integrations`** (was `workspace_integrations`) — `id uuid pk`, `user_id uuid` (which team member connected it), `toolkit_slug text` (`slack`|`gmail`), `composio_account_id text`, `connected_at`, `metadata jsonb`. Unique `(user_id, toolkit_slug)`.

### Widget secret
- **`_sys_widget_secrets`** — singleton table: `singleton bool default true primary key check (singleton = true)`, `secret_hash text` not null (we store hash + verify by recomputing; raw secret only shown once at creation), `created_by uuid`, `created_at`, `rotated_at timestamptz`. The leading underscore signals "system" — not in the auto-API surface; read/write via functions only.

### Commodity-tier knowledge (RAG)
- **`docs_sources`** — `id uuid pk`, `url text` (nullable for uploaded file sources), `source_kind text` (`web|sitemap|uploaded_file|github_readme`), `display_name text`, `rag_collection_id text` (the Butterbase RAG collection id this source feeds), `last_crawl_at timestamptz`, `last_crawl_status text` (`ok|partial|failed`), `last_crawl_error text`, `chunk_count int default 0`, `crawl_config jsonb` (include/exclude regex patterns, max-depth, etc.), `created_by uuid`, `created_at`, `updated_at`. Index: `(source_kind, last_crawl_at)`. **No RAG content itself in Postgres** — content lives in the platform's RAG collection; this table is the index/cursor only.

### Audience-scoped disclosure (safety floor)
- **`outbound_disclosure_violations`** — `id uuid pk`, `ticket_id uuid fk→support_tickets cascade`, `message_id uuid` (nullable; the draft that triggered the violation), `attempted_field_path text` (e.g. `substrate.entity.attrs.mrr_usd`), `redaction_applied text` (the substituted value, e.g. `[redacted]`), `severity text` (`info|warn|block`), `agent_thread_id uuid`, `created_at`. Index: `(ticket_id, created_at)`. **Append-only audit trail.** A `block`-severity row means the agent's draft was withheld and re-prompted; `warn` means a field was stripped and the draft proceeded.

### Out of v1 (deferred — DO NOT build now)
- `notes` (entity-attached freeform notes) — defer; founder can edit ticket inline in v1.
- `saved_views` / `custom_fields` — defer; the inbox has a fixed shape for v1.
- `attachments` — defer; widget v1 is text-only.

## Substrate projections (what we propose, when, from what)

Audit trail per `substrate-boundaries`. All writes use `ctx.substrate.propose(capability, payload)` — never direct SQL into substrate tables. Read access (entities + memory search) is via `ctx.substrate.findEntities` / `searchMemory`.

**What we READ from substrate (no writes from this recipe):**
- **Person entities** — `findEntities({ type: 'person', q: customer_email })`. Populated by the CRM's `ingest-gmail` with `canonical_keys: { email }`. Plan, MRR, tenure, history attributes come from here. This recipe never creates person entities — if a customer emails support but isn't in substrate yet, we surface that to the founder as "unknown customer" and let the CRM resolve it on the next gmail sync. We do NOT auto-create entities from support contact.
- **Company entities** — same pattern, `canonical_keys: { domain }`.
- **Memory** — `searchMemory(query, { kinds: ['decisions', 'commitments', 'learnings'] })` for richer context when diagnosing (e.g., "we committed to a fix for this customer last week").

**What we WRITE to substrate (all via propose):**

| When | Capability | Payload sketch | Why this is substrate-worthy |
|---|---|---|---|
| Any ticket state change (open, draft, escalated, resolved) | `upsert_source_artifact` | `{ kind: 'support_ticket', external_system: 'support_recipe', external_id: ticket_id, title, content: <header + transcript>, attrs: { status, topic_tag, current_diagnosis, diagnosis_history, escalations, message_count, … }, links: { entity_ids: [customer_substrate_id] } }` | ONE rolling artifact per ticket (not split intake/diagnosis). `sync-ticket-artifact` is invoked by every state-changing function (widget-ingest, widget-followup, auto-reply-worker, send-draft-reply, execute-escalation, DO) and re-upserts the whole artifact. Idempotent by `(external_system, external_id)`. |
| Founder approves an agent-proposed action | `<the action's capability>` — e.g. `support.resend_verification_email`, `support.retry_failed_webhook`, `support.flag_as_bug`, `support.apply_account_credit` | `{ ticket_id, customer_substrate_id, ...action-specific params }` | This is the governed propose-policy-execute-log loop. Substrate is the action ledger. Local `agent_proposals` mirror; substrate `act_…` is canonical. |
| Escalation fires | `support.escalate_to_human` | `{ ticket_id, target_channel: 'slack' \| 'email', target_config_id, context_snapshot: {who, plan, mrr, diagnosis, actions_tried}, idempotency_key }` | The outbox-bound action delivers via the registered webhook target. Audit trail of every escalation lives in the substrate ledger. |
| Pattern signal becomes "surfaced" (cross-cutting issue confirmed) | `record_learning` | `{ title, content, related_entity_ids?: [], evidence_ref: { signal_kind, signal_key, sample_ticket_ids } }` | Once a pattern crosses our surfacing threshold ("3+ customers hit this in 24h"), it's a substrate-worthy learning the founder's Claude can later cite. Raw counts stay local; the confirmed insight projects. |
| Founder explicitly commits to a customer via the inbox (e.g. "I'll ship this fix by Friday") | `record_commitment` | `{ title, owner_entity_id: founder, beneficiary_entity_id: customer_substrate_id, due_date, source_artifact_id: <the support_ticket_intake artifact> }` | Cross-system commitment. The CRM and any other recipe needs to know. Founder triggers this explicitly with a UI affordance ("mark as commitment") — never auto-inferred. |
| Founder explicitly converts a recurring drafted-reply pattern into a policy (UI: "make this a policy") | `record_decision` | `{ title, kind: 'policy_decision', rationale: '<why + policy text + scope + source ticket>' }` | E.g. "we offer 50% credit for outages > 24h". The CRM, billing, and future support drafts read this as ground truth. Founder-triggered only — agents never auto-infer policies. Kind string is the canonical `policy_decision` per substrate schema; `'policy'` is rejected. |

**What we deliberately do NOT propose:**
- **Scraped docs / RAG content** — substrate-boundaries category 1 (high-volume operational) + category 9 (computed projections). Pages live in the Butterbase RAG collection, not substrate. Substrate only takes the *distilled* outcomes of using that knowledge (resolved tickets, policies).
- Ticket open/close events as substrate activities — recipe workflow state.
- Individual `support_messages` rows — high-volume operational; the original intake is captured as one source_artifact, subsequent back-and-forth stays local.
- Per-agent-step `agent_messages` (tool calls, intermediate reasoning) — recipe-internal.
- Drafts the founder rejected — local-only; substrate sees only confirmed actions.
- Low-confidence pattern signals before they cross the surfacing threshold — would pollute substrate per category 12 (tentative inferences).
- Founder's UI preferences, autonomy dial settings, skill edits — category 2 (UI/UX state, configuration).
- `outbound_disclosure_violations` rows — recipe-internal audit, not a substrate signal.
- `docs_sources` rows — recipe-internal configuration.

**Outbox targets (for executed actions):**
We register webhook targets for each action capability so when substrate verdicts to execute, our handler runs the actual side effect:
- `support.resend_verification_email` → webhook into our `execute-resend-verification` function → calls the customer app's auth API.
- `support.retry_failed_webhook` → webhook into `execute-retry-webhook` → re-fires the original webhook via the customer app's queue.
- `support.flag_as_bug` → webhook into `execute-flag-bug` → writes a bug record into the customer app's issue tracker (or the support recipe's own `flagged_bugs` table if the app has no tracker).
- `support.apply_account_credit` → webhook into `execute-apply-credit` → calls the customer app's billing API. **Always requires human approval regardless of yolo_mode.**
- `support.escalate_to_human` → webhook into `execute-escalation` → sends Slack DM via Composio or Gmail via Composio, depending on `escalation_targets.channel`.

Each outbox webhook uses HMAC verification + `ctx.idempotency.claim(action_id, { scope: 'substrate_outbox' })` so substrate retries are safe.

## RLS

Single-tenant model — the app instance itself IS the tenant boundary. Within an app, the only access question is "are you a team member, and what's your role?" No `workspace_id` joins. Customer-widget writes happen in service-role functions, NOT via RLS — see "Widget path" below.

### The team-membership predicate

All operational tables use the same shape:

```sql
USING (
  EXISTS (SELECT 1 FROM memberships WHERE user_id = auth.uid())
)
WITH CHECK (
  EXISTS (SELECT 1 FROM memberships WHERE user_id = auth.uid())
)
```

Sensitive tables (`support_skill`, `autonomy_settings`, `escalation_targets`, `app_allowlist`, `_sys_widget_secrets`) tighten the predicate further to admins:

```sql
USING ( EXISTS (SELECT 1 FROM memberships WHERE user_id = auth.uid()) )
WITH CHECK ( is_team_admin() )
```

with a helper:

```sql
CREATE FUNCTION is_team_admin() RETURNS bool AS $$
  SELECT EXISTS (
    SELECT 1 FROM memberships
    WHERE user_id = auth.uid() AND role IN ('owner', 'admin')
  )
$$ LANGUAGE sql STABLE;
```

### Widget path — the special case

The customer widget is embedded in the customer's app and authenticates **against the customer's app**, not against this support app. The widget therefore does NOT carry a JWT we can verify natively. It authenticates to us via HMAC.

**Install flow:**
1. Founder goes to console → Settings → Widget install. We generate a `widget_secret` (HMAC key), store the hash in `_sys_widget_secrets`, show the raw secret ONCE.
2. Customer's app, server-side, signs `{ user_id, email, name?, plan?, ts }` with the secret to produce `user_signature`.
3. Customer's frontend passes `{ user_payload, user_signature }` to the widget bundle.

**Inbound write:**
- Widget POSTs to `widget-ingest` function (`auth: 'none'`, runs as service-role).
- Function verifies HMAC, rejects on mismatch or stale timestamp (>5 min window).
- Function resolves `customer_substrate_id` by email via `ctx.substrate.findEntities({ type: 'person', q: email })`.
- Function inserts `support_tickets` + `support_messages` rows — bypasses RLS because service-role.
- Function proposes `upsert_source_artifact` to substrate for the intake message.

**Why this is safe:** the secret is per-app, only the customer's server holds it (not the browser), HMAC + timestamp prevents replay. End-users of the customer's app never touch our DB via RLS — only via the service-role function, which enforces all scoping in code. Pattern matches the CRM's `accept-invite`.

**Widget read path (ticket history for same end-user):**
- `widget-fetch-history` function (`auth: 'none'`, service-role).
- Same HMAC verification.
- Reads `support_tickets` filtered by `customer_substrate_id` in code.
- Returns only that user's tickets.

### Founder console JWT path

Founders + team authenticate via the support app's own auth (magic link primary, email/password fallback — see Auth section). Their JWT carries `auth.uid()`, which the RLS predicates above resolve via `memberships.user_id`. Standard pattern.

### Substrate access

The DO + functions reach substrate via `ctx.substrate` (auto-wired because the app is linked to the founder's `substrate_user_id`). No RLS concern on our side — substrate scopes by the linked owner.

## Auth

**Single sign-in model: magic link by default, email/password as fallback.** No OAuth providers in v1 (can add post-v1 without disrupting the model — the SDK supports both side-by-side).

### Endpoints in use (Butterbase native)

| Flow | API | SDK |
|---|---|---|
| Magic-link (primary) | `POST /auth/{app_id}/magic-link` → 6-digit code emailed | `auth.sendMagicLink(email)` |
| Magic-link verify | `POST /auth/{app_id}/magic-link/verify` → tokens | `auth.verifyMagicLink(email, code)` |
| Email/password signup (fallback) | `POST /auth/{app_id}/signup` | `auth.signUp({ email, password })` |
| Email/password login (fallback) | `POST /auth/{app_id}/login` | `auth.signIn({ email, password })` |
| Refresh | `POST /auth/{app_id}/refresh` | automatic via SDK |
| Logout | `POST /auth/{app_id}/logout` | `auth.signOut()` |
| Profile | `GET /auth/{app_id}/me` | `auth.getUser()` |

Magic-link characteristics (per docs.butterbase.ai):
- 6-digit code, 15-minute expiry, single-use.
- Frictionless signup — new users are auto-created on send; first verification logs them in.
- `isNewUser` flag surfaced in the post-auth hook.
- Post-auth hook event: `magic_link_login` (provider: `magic_link`).
- Email-verified is set automatically on verify.

### Bootstrap flow (the post-auth hook)

We configure a single post-auth hook on the app via `manage_auth_config` (action: `configure_auth_hook`). The hook is fire-and-forget — never delays the user's token.

Hook responsibilities (in order, idempotent):

1. **Allowlist check.** Look up the user's email in `app_allowlist`.
   - If found and `active = true` → continue.
   - If not found AND `memberships` is empty → **first-user bootstrap.** Insert the email into `app_allowlist` (created_by = self) AND insert a `memberships` row with `role = 'owner'`. Continue.
   - If not found AND `memberships` already has rows → the user signed in but isn't on the team. **Do not insert.** The frontend's first call will see `memberships` empty for this user_id and show a "you don't have access" screen.

2. **Memberships ensure.** If the user is allowlisted but doesn't have a `memberships` row yet, insert one with `role = <matching app_allowlist.default_role>` (the admin pre-assigned the role when inviting them; this completes their onboarding on first login). Domain-allowlist matches (`entry_type='domain'`) default to `'member'`.

3. **Optional substrate provision.** On `isNewUser=true` and `memberships.role='owner'`, ensure the app is linked to a substrate (`POST /v1/apps/{app_id}/link-substrate` if not yet linked). For this recipe specifically: the substrate is linked manually during preflight to the founder's existing substrate (which is also the CRM's substrate), so this step is a no-op in normal flow.

4. **Audit.** Insert an `activities` row: `kind='auth.bootstrap'` or `kind='auth.login'`.

The hook is implemented as a function `auth-bootstrap-hook` (HTTP-trigger, `auth: 'none'`, but verifies the Butterbase auth-hook signature header — see auth docs for the hook signing scheme).

### Why no OAuth in v1

The founders we're shipping to all have email addresses. Magic link is a strictly better UX than OAuth for that audience (no provider redirect dance, no consent screen, works with any email identity including custom domains). OAuth becomes valuable when:
- The recipe is sold to enterprise teams who require SSO. Out of scope for v1.
- The customer wants to onboard with their existing Google/GitHub identity for convenience. Magic link gets there in one click via Gmail's autofill.

Adding OAuth later is a one-call config (`manage_oauth` `configure`); the SDK's `signInWithOAuth` works alongside magic link with no schema changes.

### Token lifetimes

Default per Butterbase: access token 1h, refresh token 7d. Acceptable for v1; we can tune via `manage_auth_config` `update_jwt` if the founder console feedback suggests otherwise.

### What about the customer widget?

The widget does NOT use any of these endpoints. The widget authenticates via HMAC (see RLS → Widget path). End-users of the customer's app are NEVER users of this support app — they have no auth identity here. They appear only as `customer_substrate_id` references on tickets.

## AI

Uses Butterbase's built-in AI model gateway (`manage_ai` MCP / `POST /v1/{app_id}/chat/completions` + `/embeddings`). No external SDK. Configured once during `journey-preflight` via `manage_ai action: update_config`.

### Models (v1)

| Role | Model | When | Why |
|---|---|---|---|

| **Classification** (issue_type tagging, pattern fingerprinting, "is this a duplicate of an open ticket?") | `anthropic/claude-haiku-4-5-20251001` | Lightweight subtasks called from the DO before the main reasoning pass | ~10× cheaper, sub-second. ### Per-ticket budget guardrails (hardcoded in DO for v1)

Enforced inside the `SupportTicketDO`, not at the platform layer. Constants live at the top of the DO source and are overridable via env vars:

| Constant | v1 default | Purpose |
|---|---|---|
| `MAX_INPUT_TOKENS_PER_TICKET` | 50_000 | Sum across all LLM calls for one ticket's diagnosis + draft loop |
| `MAX_OUTPUT_TOKENS_PER_TICKET` | 5_000 | Sum of generation tokens |
| `MAX_LLM_CALLS_PER_TICKET` | 12 | Hard cap on agent-loop iterations |

### Streaming

Agent draft generation uses `"stream": true` on chat completions. The DO forwards SSE chunks over its WebSocket to the founder UI so the founder watches the draft form in real time. Streaming is also used during diagnosis so the founder sees the agent's reasoning trace incrementally.

### Audience-scoped disclosure (interaction with AI)

The AI gateway is NOT constrained directly. The agent is free to generate any draft. The outbound disclosure filter (library, runs inside `send-draft-reply` and inside the DO's escalation step) inspects the draft AFTER generation:
- Walks the text for substrings that match whitelisted-only substrate field values that AREN'T in the customer's own scope.
- Strips matches, substitutes `[redacted]`, logs an `outbound_disclosure_violations` row.
- If severity = `block` (e.g., redaction makes the draft incoherent), throws the draft back to the DO with a "rewrite without referencing internal fact X" hint and re-runs the agent loop. Counts against `MAX_LLM_CALLS_PER_TICKET`.

This keeps the safety constraint structural without bloating the prompt with rules the model could ignore.

## RAG

The commodity-tier engine. Uses Butterbase's built-in RAG (`manage_rag_content` + `rag_query`) — no custom pgvector code, no chunking pipeline.

### Collections

**Exactly one collection per cloned recipe: `support-docs`.**

```json
{
  "name": "support-docs",
  "access_mode": "shared"
}
```

- `shared` access mode — every authenticated team member can query (RLS via `memberships` + access_mode interaction). End-customers via the widget never query directly; the DO + functions do, running service-role.
- We do NOT create one collection per docs_source. Sources are distinguished by metadata at ingest time + `filter` at query time. Simpler ops, fewer collections to manage.

### Ingestion sources

| Source | Path | Metadata stamped per doc |
|---|---|---|
| **URL crawl** (front-door onboarding) | `ingest-docs` → crawler walks the page tree → each page becomes one `manage_rag_content` `ingest` call with `text` body | `{ docs_source_id, url, content_hash, crawled_at, source_kind: 'web' }` |
| **Uploaded file** | `ingest-docs` → file already in `docs_uploads` bucket → `manage_rag_content` `ingest` with `storage_object_id` | `{ docs_source_id, file_name, content_hash, uploaded_at, source_kind: 'uploaded_file' }` |
| **Sitemap** | Crawler reads sitemap.xml, paginates URLs, same per-page ingest as web crawl | `{ docs_source_id, url, content_hash, crawled_at, source_kind: 'sitemap' }` |

**Chunking** is handled by Butterbase RAG — we don't override. Each page is one ingest call; the platform splits it into embedding-sized chunks under the hood. This gives us per-page deletion + per-page recrawl semantics without managing chunk lifecycles ourselves.

### Refresh / staleness handling

`refresh-docs` cron (Sundays 04:00 UTC) walks `docs_sources` rows. For each:

1. Re-crawl the URL (or re-read the uploaded file).
2. Hash each page's text. Compare to `content_hash` stored on the matching RAG document via `manage_rag_content` `list`.
3. **Unchanged** → skip (no re-embedding cost).
4. **Changed** → `manage_rag_content` `delete` the old doc, then `ingest` the new one with the new hash.
5. **Gone (404 on web; file removed)** → `manage_rag_content` `delete` the orphan doc.
6. **New** (URL was added since last crawl, e.g. a new help-center article) → `ingest` fresh.

Updates `docs_sources.last_crawl_at`, `last_crawl_status`, `chunk_count`, `last_crawl_error`. Founder console surfaces these per source.

### Query-time retrieval (the agent's `search_docs` tool)

The DO's agent loop exposes `search_docs` as a tool. Signature:

```typescript
async search_docs({
  query: string,
  top_k?: number = 8,           // higher than RAG default to give agent room
  threshold?: number = 0.65,    // tune from real data; lower = more recall, more noise
  source_kinds?: string[],      // optional: restrict to ['web'] or ['uploaded_file']
  docs_source_ids?: string[],   // optional: restrict to specific sources
}): Promise<Array<{
  text: string,
  score: number,
  metadata: { url?, file_name?, docs_source_id, crawled_at | uploaded_at, source_kind },
}>>
```

Internally calls `rag_query` with `synthesize: false` (the agent does its own synthesis with full ticket + substrate context — we don't want a sub-model collapsing chunks before the main reasoning pass sees them).

**Why `synthesize: false`:** the RAG synthesis default model is `claude-haiku-4-5` which is fine, but the agent loop needs raw chunks to (a) cite specific URLs in the draft reply, (b) detect "low confidence" (top score below a threshold) for escalation gating, (c) combine chunks with substrate evidence in the deep tier.

### When the agent calls `search_docs`

Hardcoded in the agent's system prompt + loop:
- **Always on first turn** — every diagnosis starts with a docs search using a paraphrased version of the customer's question. This is the commodity-tier baseline.
- **On follow-up questions** — if the customer adds a follow-up, the agent re-queries with the cumulative thread context.
- **NOT on substrate-deep findings** — once the agent has read substrate and formed a substrate-grounded diagnosis, it doesn't re-query docs unless the draft needs supporting citations.

### Citation rendering

Draft replies include citations like `[1]` `[2]` mapped to a footer block listing the source URL + last-crawled date. Founder UI surfaces citations as clickable links. Customer-facing widget renders them the same way (citations are not internal-only — they're literally the customer's own documented policies).

### Confidence + escalation gating (commodity tier)

`search_docs` returns chunks with `score`. The agent's escalation rule (per-iteration):

| Condition | Action |
|---|---|
| Top chunk score ≥ 0.80 | Draft reply confidently |
| Top chunk score 0.65–0.80 | Draft reply but flag `confidence: 'low'` on the agent_proposal |
| Top chunk score < 0.65 | Don't draft. **Escalate** to human via `support.escalate_to_human` with context `"docs search returned nothing above threshold for: <query>"`. |

Numbers are placeholders to tune from real data. They live as constants in the DO source, overridable via env vars.

### Interaction with substrate (deep tier)

In deep mode, both tools run:
1. `search_docs` (commodity baseline) → returns docs chunks.
2. `read_substrate` → returns customer entity + recent product source_artifacts + relevant memory.

The agent's reasoning pass sees both inputs and writes a diagnosis grounded in BOTH. Citations include docs links AND substrate references (e.g., "based on your upgrade event from 2026-06-15 [substrate:act_…] and our refund policy [1]…"). Substrate-side citations only appear in INTERNAL views (founder console) — the outbound disclosure filter strips them before the customer sees the reply.

### Empty-collection bootstrap (the ≤60s magic moment)

The recipe ships with `support-docs` collection **already created** (via seed migration). On clone, the collection exists but is empty. First successful `ingest-docs` call (paste URL in the wizard) populates it. The agent's `search_docs` tool gracefully returns `[]` when the collection is empty — in that state, the agent always escalates to human until docs land.

### What we deliberately do NOT do with RAG in v1

- **Per-customer / per-end-user RAG collections** — overkill. One `support-docs` collection per recipe is enough.
- **Project scraped pages into substrate as `source_artifacts`** — explicitly out per substrate-boundaries (high-volume operational + computed projections). Pages live in RAG, NOT substrate. Only *surfaced cross-ticket pattern learnings* and *founder-confirmed policies* project.
- **Synthesize=true at query time** — the agent's own LLM handles synthesis with full context.
- **Custom embedding model** — stick with `openai/text-embedding-3-small` for v1; can swap to `text-embedding-3-large` later if recall feedback suggests.
- **Cross-recipe RAG sharing** — each cloned recipe has its own collection. No global support knowledge.

### Cost budget (v1, sonnet-pricing baseline)

- Ingest: one-time cost per source. A medium help-center (~200 articles) ≈ ~$0.50–$2 in embedding credits.
- Query: embedding for the user's question (~$0.0001) + the LLM reasoning pass. RAG itself is ~free per query.
- Refresh: only changed pages re-embed. Weekly cost ≈ ~$0.05–$0.20.

Updates to function table — `ingest-docs` and `refresh-docs` are the load-bearing functions (already listed in Functions section). No new functions needed for RAG.

## Realtime

Three different live channels — used for different things, deliberately not overlapping.

| Channel | Carries | Source | Frequency |
|---|---|---|---|
| **Postgres Realtime (`manage_realtime configure`)** | Low-frequency persisted state changes the founder console reflects in lists | Butterbase platform | Per row write |
| **Durable Object WebSocket** (`/_do/SupportTicketDO/<ticket_id>`) | High-frequency live agent stream (LLM tokens, tool calls, reasoning trace) | The DO itself | Per token / per step |
| **Substrate WebSocket** (`/v1/me/substrate/stream`) | Cross-app substrate activity — CRM updates, action ledger entries from other recipes | Butterbase platform | Per substrate write |

The founder console connects to all three. The customer widget connects to NONE in v1 — it polls via `widget-poll-replies`. (Public WS exposure for the widget is post-v1.)

### Tables with Postgres Realtime ENABLED

Configured once during build via `manage_realtime` `action: configure`. RLS applies as usual — each team-member subscriber only receives change events for rows they could read normally.

| Table | Subscribed-to events | Why |
|---|---|---|
| `support_tickets` | INSERT (new tickets arriving from widget), UPDATE (status transitions: drafting→awaiting_approval→sent→resolved) | Inbox list updates without polling. Sort order by `last_message_at desc`. |
| `support_messages` | INSERT (customer follow-up arrives, or the DO writes an agent_draft) | Ticket detail view updates the conversation thread live. |
| `agent_proposals` | INSERT (new proposal needing approval), UPDATE (status transitions: pending→approved/rejected/expired) | The "approvals required" badge + the proposal card list update live. |
| `diagnoses` | INSERT (DO produced a new diagnosis), UPDATE (`superseded_at` set when rerun) | Current-diagnosis card refreshes; reruns visibly replace stale diagnoses. |
| `escalations` | INSERT, UPDATE (`status` queued→sent/failed) | Ticket-detail "escalation status" line + a top-bar notification on failure. |
| `pattern_signals` | UPDATE WHERE `surfaced` transitions `false→true` | Top-of-inbox banner: "3 customers hit error X this week — review pattern". |

### Tables with Postgres Realtime explicitly DISABLED

| Table | Why no realtime |
|---|---|
| `agent_threads`, `agent_messages` | High-frequency log-of-record. The live stream is the DO's WS — DB writes happen on step-complete, after the stream has already shown the founder. Subscribing here is redundant. |
| `app_allowlist`, `memberships` | Fire-and-forget admin edits; the editor refetches on save. |
| `support_skill`, `autonomy_settings`, `escalation_targets` | Same — admin edits via dedicated forms. |
| `team_integrations`, `integration_state` | Background sync state; UI re-fetches on settings open. |
| `activities` | Log table; UI tails on demand. |
| `docs_sources` | Crawl status updates via the cron — founder console polls during active ingestion (status flips quickly) and refetches the page when crawl completes. |
| `_sys_widget_secrets` | Singleton, almost never changes. Subscription would be wasteful. |
| `outbound_disclosure_violations` | Audit log; surfaced contextually on the ticket where it happened, not via subscription. |

### Durable Object WebSocket

The `/_do/SupportTicketDO/<ticket_id>` endpoint accepts both HTTP and WebSocket upgrades. The founder UI opens a WS to the DO when the founder OPENS a ticket detail view. Carries:

- Live LLM token stream during diagnosis + draft (SSE chunks forwarded as WS frames)
- Tool-call lifecycle events: `{kind:'tool_call_start', tool:'search_docs', args:{...}}`, `{kind:'tool_call_result', tool:'search_docs', summary:{...}}`
- Agent reasoning steps as they emit
- Founder commands going the other way: `{cmd:'diagnose'}`, `{cmd:'draft'}`, `{cmd:'rerun_with_hint', hint:'...'}`, `{cmd:'pause'}`

Closes when the founder navigates away from the ticket. The DO persists final state to Postgres on step-complete (`agent_messages`, `diagnoses`, `agent_proposals`), and *those* changes propagate to other team members via Postgres Realtime — so a teammate who has the same ticket open in another browser sees the persisted state arrive even though they're not connected to the DO's WS.

(Only ONE founder at a time runs the live agent loop for a given ticket. The DO's WS upgrade handler accepts the first connection and rejects subsequent ones with a "already in use" frame. Future enhancement: multi-watcher fan-out. v1 = single-driver semantics.)

Authentication: the DO verifies the team-member JWT on the WS upgrade (`Authorization: Bearer` on the upgrade or `?token=` query param). Rejects non-members.

### Substrate WebSocket (consumed by founder console directly)

The founder's substrate is shared across apps. The console subscribes to `wss://api.butterbase.ai/v1/me/substrate/stream` (after exchanging a one-shot ticket via `/v1/me/substrate/ws-ticket`) to see:

- Action ledger entries from OTHER recipes (CRM, etc.)
- Entity attribute changes (the CRM enriched a customer → the support inbox's customer card refreshes)
- Source artifact additions (a meeting transcript was projected → relevant tickets gain new context)

The recipe does NOT proxy this stream. The founder console handles it directly via the Butterbase SDK or the platform JWT it already has. The substrate stream is the "company brain" channel; the recipe is a consumer, not a relay.

### Customer widget — polling (v1)

`widget-poll-replies` is called every ~5s by the open widget when there's an active ticket. Returns new `support_messages` since a client cursor. Trade-offs:

- Pros: simple, no HMAC-tokened WS exchange needed, works behind every proxy.
- Cons: 5s perceived lag; constant DB hits from the widget.

Post-v1: public WS endpoint with HMAC token exchange (mirrors substrate's `/ws-ticket` pattern). Same wire protocol as the founder DO connection on the WS side, with a tighter capability scope.

### Realtime cost expectations

Butterbase Realtime is included in the plan; no per-message charge. The DO's WS is on the DO bundle's CPU + duration meters. Sub-cent per ticket conversation in v1.

## Durable Objects

The heart of the agent runtime. **One DO class, multi-instance: `SupportTicketDO`** with instance id = `ticket_id`. One DO instance per support ticket. Holds the live agent loop in memory + transactional KV; streams to the founder UI via WebSocket; persists final-state rows to Postgres.

DO constraints from the platform: single-file source, no npm imports (only `cloudflare:workers`), 128 KB per KV key, 10 MB bundle compressed, 5 DO classes per app max. We use **1 of 5** — leaves headroom for post-v1 additions (e.g., a `PatternSurfaceDO` for live pattern detection).

### Instance lifecycle

| Phase | What happens |
|---|---|
| **Cold start** | First request to `/_do/SupportTicketDO/<ticket_id>` after eviction. Constructor loads from `state.storage` (KV). If KV is empty (first-ever request for this ticket), hydrates from Postgres via auto-API + reads ticket / messages / latest diagnosis. |
| **Hot** | In-memory state authoritative. KV used for crash recovery + cumulative budget. Postgres updated on step-complete. |
| **Idle** | No active WS connection. DO instance remains alive ~5 min, then Cloudflare evicts. KV survives eviction. |
| **Eviction** | In-memory state discarded. Next request triggers cold start. |

### In-memory state (rebuilt on cold start)

```typescript
type SupportTicketDOState = {
  ticket_id: string,
  ticket_status: TicketStatus,
  customer_substrate_id: string | null,
  customer_email: string,
  agent_thread_id: string,
  messages: AgentMessage[],            // conversation + tool calls (truncated to last N for prompt)
  current_diagnosis: Diagnosis | null,
  pending_proposal_ids: string[],
  agent_loop_state: 'idle' | 'diagnosing' | 'drafting' | 'escalating' | 'errored',
  connected_ws: WebSocket | null,
  driver_session_id: string | null,    // single-driver lock
  budget_used: { input_tokens: number, output_tokens: number, calls: number },
  last_event_at: number,
}
```

### Transactional KV layout (`state.storage`)

| Key | Value | Why KV (not Postgres) |
|---|---|---|
| `meta` | `{ ticket_id, agent_thread_id, ticket_status, last_event_at }` | Single fetch on cold-start; fast |
| `budget` | `{ input_tokens, output_tokens, calls, hour_window_start, tickets_this_hour }` | Survive crashes/evictions; bursting protection |
| `lock` | `{ session_id, acquired_at, last_heartbeat_at }` | Single-driver semantics; survive instance crash |
| `msg:<message_id>` | One agent message (≤128 KB; we truncate large `tool_results` to a summary) | Per-message granularity for replay |
| `msg_index` | `{ message_ids: string[] }` (ordered) | Fast list rebuild on cold start |
| `proposal:<id>` | Local mirror of pending proposal pre-substrate-write | Crash recovery if process dies between `ctx.substrate.propose` returning and Postgres insert |

### Agent tool surface (what the agent CAN do)

Defined as function declarations registered with the LLM. **This is the structural safety boundary** — the agent literally cannot do anything outside this list. No `fetch`, no direct DB writes, no direct substrate writes outside `propose_*`.

| Tool | What it does | Effect surface |
|---|---|---|
| `search_docs(query, top_k?, threshold?, source_kinds?, docs_source_ids?)` | RAG query via `rag_query` | Read RAG collection |
| `read_substrate_entity(by_id_or_email)` | `ctx.substrate.findEntities` + `getEntity` | Read substrate |
| `search_substrate_memory(query, kinds[])` | `ctx.substrate.searchMemory` | Read substrate |
| `list_customer_source_artifacts(customer_substrate_id, kinds[], limit)` | List artifacts projected by the customer's main app for this user | Read substrate |
| `read_recent_ticket_history(customer_substrate_id, limit)` | Postgres query via service-role auto-API | Read recipe DB |
| `propose_diagnosis(summary, evidence, confidence)` | Inserts `diagnoses` row (and marks prior superseded) + proposes `upsert_source_artifact` to substrate (kind: `support_diagnosis`) | Write recipe DB + substrate |
| `propose_draft_reply(body, citations[], confidence)` | **Runs body through the outbound disclosure filter** (see below). If passes: inserts `agent_messages` (role=`assistant`) + `support_messages` (role=`agent_draft`). | Write recipe DB |
| `propose_action(capability, payload, rationale)` | `ctx.substrate.propose(capability, payload, idempotency_key)` + insert `agent_proposals` row mirroring local | Write recipe DB + substrate |
| `propose_escalation(reason, urgency)` | `propose_action('support.escalate_to_human', { ticket_id, target_channel: <default>, context_snapshot, ... })` | Write substrate via above |
| `request_followup_question(question)` | The agent decides it can't resolve without more info from the customer. Writes a draft asking the customer for clarification, same path as `propose_draft_reply`. | Write recipe DB |

The agent CANNOT:
- Open arbitrary fetch calls.
- Read substrate fields outside the customer's own scope (the `read_substrate_*` tools are scoped — see below).
- Mutate substrate outside `propose_*`.
- Mark a ticket resolved (founder action only — `send-draft-reply` function with `mark_as_resolved`).
- Change `support_skill`, `autonomy_settings`, `escalation_targets`, `app_allowlist` (no tools cover these).
- Call other DOs.

### Two substrate access scopes — the safety floor

The DO holds TWO substrate accessors, scoped differently. This is how "audience-scoped disclosure" is enforced structurally.

```typescript
class SupportTicketDO {
  private substrate_internal: SubstrateClient;  // ctx.substrate as-is — full read
  private substrate_outbound: ScopedSubstrateClient;  // wrapped, whitelist-only
  // ...
}
```

| Accessor | Scope | Used by |
|---|---|---|
| `substrate_internal` | Full read of the founder's substrate (per platform RLS) | The agent's reasoning tools (`read_substrate_entity`, `search_substrate_memory`, `list_customer_source_artifacts`) |
| `substrate_outbound` | Whitelist: customer's own entity attrs minus internal-tagged fields; customer's own ticket history; founder-confirmed policies tagged `public: true`. **No MRR, no internal notes, no other customers' data, no untagged commitments.** | The outbound disclosure filter only |

The whitelist is hardcoded in the DO source. It's NOT editable via `support_skill`. Changing it requires editing the recipe code. This is intentional — it's the safety floor.

### Outbound disclosure filter (the load-bearing safety code)

Lives in the DO source as a shared library; the `send-draft-reply` function imports the same library so founder-edited drafts get the same treatment.

Algorithm:

```typescript
async function outboundFilter(
  draft: string,
  ctx: { ticket_id, customer_substrate_id, agent_thread_id },
  substrate_outbound: ScopedSubstrateClient,
): Promise<{ filtered_draft: string, violations: Violation[] }> {
  // 1. Substring scan for known internal field values.
  //    Pull all substrate field values currently scoped as "internal-only" for this customer
  //    via substrate_outbound's INVERSE-whitelist lookup (returns redacted handles).
  //    Search the draft for any of those values.
  //
  // 2. Reference resolution.
  //    Scan the draft for substrate IDs (regex: ent_..., act_..., dec_..., com_...).
  //    Verify each is in the customer's own scope via substrate_outbound.
  //    Unresolvable IDs → redact.
  //
  // 3. Generic regex patterns.
  //    Other customers' email addresses (anything ending in domains other than the customer's).
  //    Currency-MRR patterns when not in a citation context.
  //    Internal codenames from a hardcoded blocklist.
  //
  // 4. For each match: replace with [redacted] + record Violation.
  //
  // 5. Severity ranking:
  //    - info: a substrate ID was scrubbed but the surrounding text is fine.
  //    - warn: a value was redacted; draft is coherent.
  //    - block: redactions make the draft incoherent (e.g., a key noun was removed).
  //
  // 6. If any violation is severity=block, throw RedraftRequired with a hint
  //    ("draft referenced internal fact X — please rewrite without naming it").
  //    The agent loop catches this, re-prompts, and burns one of the call-budget slots.
  //    Three block-redrafts in a row → give up, propose_escalation.
}
```

Persists each Violation row to `outbound_disclosure_violations` regardless of severity.

### Agent loop (per event)

Triggered by: ticket open (initial), customer follow-up arriving, founder command via WS.

```
acquire driver lock (if WS-initiated)
load_or_hydrate_state()
emit({type:'state', agent_loop_state:'diagnosing'})

while not done and budget_remaining() and calls_under_cap():
  step = await llm.generate({
    messages: build_prompt(state),     // includes support_skill + safety floor
    tools: ALL_TOOLS,
    model: 'anthropic/claude-sonnet-4.6',
    stream: true,
  })

  forward stream tokens → WS frames

  if step.is_tool_call:
    tool_call_start → WS
    result = await execute_tool(step.tool, step.args)
    tool_call_result → WS
    append result to history
    persist agent_messages row (role='tool')

  elif step.is_final_message:
    classify final:
      ├── diagnosis only       → propose_diagnosis(...) → state='idle', done
      ├── draft reply          → propose_draft_reply(...) [filter runs] → state='idle', done
      ├── escalation           → propose_escalation(...) → state='escalating', done
      ├── needs_more_info      → propose_draft_reply(<followup question>) → state='idle', done
      └── error/giveup         → state='errored', done

  elif step.is_redraft_required:
    re-enter loop with hint appended to history

if budget_exhausted:
  write system support_message with cap explanation
  state='errored', done

release driver lock if held
persist agent_threads.status + last_event_at
```

### Founder commands (WS-driven)

| Cmd | DO behavior |
|---|---|
| `diagnose` | Start the loop fresh (mark current diagnosis superseded if any) |
| `draft` | Loop with system bias toward drafting now (rather than continuing to investigate) |
| `rerun_with_hint` | Mark current diagnosis superseded, restart loop with founder's hint appended |
| `pause` | Halt loop at next safe point, transition to `idle` |
| `escalate` (founder-forced) | Skip agent loop, propose escalation directly |
| `heartbeat` | Refresh lock's `last_heartbeat_at` |

### Single-driver coordination

WS upgrade handler checks `lock` KV:
- No lock OR lock's `last_heartbeat_at` > 60s old → acquire lock with new session id, accept connection.
- Lock held by different session → reject with WS close 1008 + reason "ticket is being driven by another user".
- Lock held by same session → resume (reconnection within ~30s after a network blip).

Lock released on: WS close clean, 60s heartbeat timeout, agent loop completion + 5s grace.

Other team members see persisted state via Postgres Realtime (`agent_messages`, `diagnoses`, `agent_proposals`) but cannot drive the live loop. Their UI shows a "currently being handled by Alice — view as read-only" banner.

### Persistence cadence

| Trigger | What gets persisted |
|---|---|
| Tool call complete | `agent_messages` row (role=`tool`) |
| Assistant turn complete | `agent_messages` row (role=`assistant`) |
| `propose_diagnosis` called | `diagnoses` row + substrate `upsert_source_artifact` |
| `propose_draft_reply` called | `agent_messages` (role=`assistant`) + `support_messages` (role=`agent_draft`) |
| `propose_action` called | `agent_proposals` (status=`pending`) + substrate `propose` returning `act_…` (recorded back into the row) |
| Loop done | `agent_threads.status`, `last_event_at` |
| Outbound filter trip | `outbound_disclosure_violations` row |
| Each significant event | `activities` row for cross-app readability |

The DO uses **service-role API key** (env var `BUTTERBASE_API_KEY` minted at clone time with auto-mint) for Postgres writes via the auto-API, bypassing RLS — same as the CRM's pattern. Service-role usage is justified: the DO acts on behalf of the team, not a specific end-user.

### Cross-team race handling

| Race | DO behavior |
|---|---|
| Customer sends widget-followup while DO is mid-diagnosis | `widget-followup` function pokes the DO (`do.handleFollowup()`). DO queues the new message, finishes current step safely, then re-runs diagnosis with the new context. |
| Founder approves a proposal while DO is still running | `approve-proposal` function calls `ctx.substrate.approve` (the source-of-truth path) and updates local mirror. DO sees the proposal status change via its next persistence-write probe; if it had been awaiting that proposal's outcome, it resumes. |
| Substrate temporarily unavailable | Tool returns error → agent retries once with backoff → if still failing, falls back to commodity-tier (docs-only) reasoning, marks confidence=`low`, recommends founder review. |
| AI gateway returns 402 (insufficient_credits) | DO halts immediately. Writes `support_messages` (role=`system`) explaining the cap. Transitions to `errored`. Founder must add BYOK or upgrade. |
| Disclosure filter blocks 3 redrafts in a row | Stop agent loop. Force `propose_escalation` with reason `"could not produce a customer-facing reply without internal disclosures"`. |

### What the DO does NOT do

- Send the actual customer-visible reply (that's `send-draft-reply` after founder approval).
- Send escalation messages (that's substrate outbox → `execute-escalation`).
- Direct table writes to admin tables (skill, autonomy, escalation_targets).
- Cross-ticket reasoning — each DO instance is per-ticket. Pattern detection happens in the `sweep-pattern-signals` cron, not in DOs.
- Crawl docs — that's `ingest-docs` / `refresh-docs`.

### Deployment

Deployed via `manage_durable_objects deploy` once at clone time. Bundle has no external imports beyond `cloudflare:workers`. All other capability calls are done via HTTP (`fetch` to the recipe's own auto-API, the platform's AI gateway, RAG, substrate).

We don't use service bindings (not supported per docs). All recipe-to-DO calls from functions are HTTP `fetch` against the `/_do/SupportTicketDO/<id>` URL — which is fine for the agent-spawn / poke patterns.

### Why the DO and not just a function

| Concern | Function | DO |
|---|---|---|
| Long-running agent loop | 5-min cap; OK for most diagnoses but fragile | No request-bound timeout; can hold state across many minutes |
| Live token stream to UI | Possible via SSE → frontend, but UI re-fetch needed across function restarts | Native WS with persistent connection |
| In-memory budget tracking | Lost between calls; must read from DB | Survives across many requests within idle window |
| Single-driver lock | Race-prone without DB transactions | DO transactional KV gives us this for free |
| Cold-start time | Cheap | Slightly more expensive (~tens of ms) but amortized across ticket lifetime |

The function-only alternative would require server-sent events + DB-backed locks + re-reading conversation state every step. DO is strictly cleaner.

## Agents

This section is about **Butterbase platform agents** (`manage_agents`) — agents the platform hosts and exposes for external clients (founder's Claude, MCP-aware tools) to call. **It is NOT about the support agent itself.** The support agent lives inside `SupportTicketDO` as in-process code; it is not a platform agent.

### Should the recipe ship platform agents at all?

The idea brief did not tag `create_agent`. Strictly per journey-plan, this section could be skipped. However, the OSS-clonable + cross-app-substrate framing argues for shipping **one small read-only agent** so the founder's Claude can fold support context into any other conversation without knowing the recipe's schema.

**Recommendation for v1: ship ONE agent, `support-overview`. The other two candidates wait for post-v1.**

### `support-overview` (v1)

| Field | Value |
|---|---|
| name | `support-overview` |
| Purpose | "Summarise current support state for this org: open tickets, who's waiting longest, surfaced patterns, escalation backlog." |
| Visibility | `authenticated` — only team members can call it. Founder's Claude calls via the team's app-scoped JWT. |
| Tool surface | Builtins: `query_table` (whitelisted to `support_tickets`, `diagnoses`, `escalations`, `pattern_signals`). Recipe functions: `fetch-ai-usage` (so it can report on AI spend). MCP: none. |
| Write tools | **None.** Read-only. |
| Default model | `anthropic/claude-haiku-4-5-20251001` — synthesis over small data; haiku is fast + cheap. |
| Daily budget | `daily_budget_usd: 1.00` per clone — caps runaway calls from a misconfigured client. |
| Rate limits | `per_user_per_hour: 60`, `per_app_per_hour: 600`. |
| Spec file | `agents/support-overview.json` — bundled with the repo snapshot. |

Example founder's-Claude invocation: *"What's the state of support this morning?"* → support-overview returns a synthesized summary citing specific ticket ids the founder can click through.

### Post-v1 agent candidates (NOT shipping)

| name | Purpose | Why post-v1 |
|---|---|---|
| `customer-history` | Given a customer (email or substrate entity id), return their full support interaction history. | Useful for the unified-substrate thesis, but the CRM recipe likely already exposes a similar entity-lookup agent we can defer to. Audit overlap before shipping. |
| `pattern-report` | Weekly digest of surfaced `pattern_signals` with severity, impact, sample tickets. | Trivial to add post-v1 once we have real `pattern_signals` data to test against. Premature without that data. |

### Agent record portability

Per the journey-plan note: agent records do NOT travel via clone replay. The spec JSON file (`agents/support-overview.json`) DOES ride along in the repo snapshot. On clone, the customer must run a re-import step (covered in the templates/README work later) — `butterbase agents import agents/support-overview.json`. The setup wizard runs this automatically as part of post-clone bootstrap.

### Why this is NOT how the support agent is exposed

The support agent (in `SupportTicketDO`) is reachable only via:
- WebSocket to `/_do/SupportTicketDO/<ticket_id>` (founder console, single-driver).
- The thin per-ticket operation functions (`approve-proposal`, `send-draft-reply`, etc.).
- The `widget-ingest` function (customer-facing entry).

It is NOT exposed as a `manage_agents` agent because:
1. Per-ticket scope — a platform agent is global; the support agent's identity is ticket-bound.
2. Stateful loop — DOs hold the multi-turn diagnosis state; platform agents are request-scoped.
3. Live streaming + driver lock — needs WS, which DOs do natively.
4. Distinct tool surface per ticket vs cross-ticket overview — the DO's tools include `propose_draft_reply` (writes a ticket-scoped row), which makes no sense as a global agent tool.

The two layers are complementary: `support-overview` is for cross-cutting summaries; `SupportTicketDO` is the per-ticket runtime.

### What about `create_agent` in the substrate ledger?

That is a substrate primitive for proposing agent creation through the substrate's governance loop. Not in v1 scope. The recipe creates `support-overview` directly via `manage_agents` at setup time — not through substrate-governed proposal.

#### Auth flow

1. `/login` — input email → call `auth.sendMagicLink(email)`. Show "check your email" screen with code input.

3. On verify success, fetch `/memberships?user_id=me`. If no row → `/no-access`. Else → `/inbox` (or `/setup` if first-time owner).

## Customer-app adapter contract

This section defines the contract between the support recipe and the customer's main product app for the **deep tier**. Two halves:

- **(A) Action handlers** — what the customer's main app implements so substrate-approved `support.*` actions actually run.
- **(B) Signal projection** — what the customer's main app pushes into substrate so the agent's diagnoses become deep.

Both flow through substrate — **no direct HTTP between the support recipe and the customer's main app**. The substrate's outbox + entity graph are the only contact surface.

### Prereqs

- The customer's main app is linked to the same `substrate_user_id` as the cloned support recipe (`manage_app link_substrate`).
- The customer's main app is reachable on a stable URL where substrate's outbox can deliver webhooks. (Native Butterbase apps: just use their function URLs. Non-native apps: any HTTPS endpoint with HMAC verification.)
- The customer holds the recipe's per-capability `signing_secret` — generated by the founder console when the customer enables a capability in the wizard.

### (A) Action handlers — registering as a substrate outbox target

For each support capability the customer wants to enable, the customer's main app calls **once at install time** (CLI, MCP, or SDK):

```typescript
// Customer's main app — run once per capability
await bb.functions.invoke('substrate-register-outbox-target', {
  capability: 'support.resend_verification_email',
  webhook_url: 'https://<customer-app>.butterbase.dev/fn/support-resend-verification',
  signing_secret: '<paste from support recipe wizard>',
});
```

Or directly via the substrate HTTP surface:

```
PUT /v1/me/substrate/outbox-targets/support.resend_verification_email
{ "webhook_url": "...", "signing_secret": "..." }
```

After registration, when the support recipe's agent proposes the capability and the founder approves, substrate POSTs the action to the registered URL.

### Common webhook contract (all capabilities)

Every action-handler webhook receives:

| Header | Meaning |
|---|---|
| `Content-Type: application/json` | — |
| `X-Butterbase-Signature: sha256=<hex>` | HMAC-SHA256 of the raw body with the `signing_secret` |
| `X-Butterbase-Delivery: <uuid>` | Per-delivery id for log correlation |
| `X-Butterbase-Action-Id: act_…` | The substrate ledger entry — use as the idempotency key |

Body shape (common envelope):

```json
{
  "action_id": "act_01H...",
  "capability": "support.<name>",
  "payload": { /* capability-specific, see below */ },
  "proposer": { "kind": "agent", "name": "support-recipe", "thread_id": "..." },
  "verdict": { "result": "auto_approved" | "requires_approval", "approved_by_user_id": "..." },
  "ticket_ref": { "ticket_id": "...", "support_recipe_app_id": "app_..." }
}
```

The handler must:

1. **Verify HMAC.** Reject 401 if mismatch.
2. **Claim idempotency** using `ctx.idempotency.claim(action_id, { scope: 'substrate_outbox' })`. If already claimed → return 200 OK with `{ duplicate: true }` (so substrate marks delivered and stops retrying).
3. **Do the work.** Capability-specific behavior below.
4. **Respond.** 2xx with optional `{ result_for_ledger: {...} }` body — substrate writes this into the action's `result` column so it's visible in the support recipe's `agent_proposals.substrate_action_id` mirror.
5. **On failure**: return 5xx (substrate retries with exponential backoff, then dead-letters) OR return 4xx with `{ permanent: true, error }` (substrate marks failed, no retry).

### Per-capability contracts (v1)

#### `support.resend_verification_email`

| Field | Spec |
|---|---|
| Payload | `{ customer_substrate_id, customer_email, ticket_id }` |
| Behavior | Re-send the customer's verification email via your auth system. Idempotent — multiple re-sends in the same hour should not flood. |
| Response | `{ result_for_ledger: { success: true, sent_to: "<email>", auth_message_id?: "..." } }` |
| Approval default | `requires_approval` (founder-approved per case) |
| Errors | 422 if `customer_email` doesn't match a known user; 5xx for transient auth-system failures |

Reference adapter (paste into a function in the customer's main app):

```typescript
// fn: support-resend-verification
export default async function handler(req: Request, ctx: any) {
  // 1. Verify HMAC
  const body = await req.text();
  if (!verifySig(req.headers.get('X-Butterbase-Signature'), body, ctx.env.SUPPORT_SIG_SECRET)) {
    return new Response('bad signature', { status: 401 });
  }
  const { action_id, payload } = JSON.parse(body);

  // 2. Idempotency
  if (!(await ctx.idempotency.claim(action_id, { scope: 'substrate_outbox' }))) {
    return Response.json({ duplicate: true });
  }

  // 3. Do the work — TODO: replace with your auth system call
  const result = await yourAuthSystem.resendVerification({ email: payload.customer_email });

  // 4. Respond
  return Response.json({ result_for_ledger: { success: true, sent_to: payload.customer_email, auth_message_id: result.id } });
}
```

#### `support.retry_failed_webhook`

| Field | Spec |
|---|---|
| Payload | `{ customer_substrate_id, ticket_id, webhook_ref: { provider, event_id, original_attempted_at } }` |
| Behavior | Re-fire the original webhook through your queue / processor. `webhook_ref` is opaque — your handler interprets it. |
| Response | `{ result_for_ledger: { retried: true, new_attempt_id: "...", result: "queued" \| "completed" \| "failed", error?: "..." } }` |
| Approval default | `requires_approval` |

#### `support.flag_as_bug`

| Field | Spec |
|---|---|
| Payload | `{ customer_substrate_id, ticket_id, title, severity: 'low' \| 'med' \| 'high', diagnosis_summary, evidence_summary }` |
| Behavior | Write a bug record into your tracker (Linear, GitHub Issues, internal `bugs` table — your choice). |
| Response | `{ result_for_ledger: { bug_id, tracker_url?: "..." } }` |
| Approval default | `requires_approval` |

#### `support.apply_account_credit` ⚠️

| Field | Spec |
|---|---|
| Payload | `{ customer_substrate_id, ticket_id, amount_cents, currency, reason }` |
| Behavior | Apply credit via your billing system (Stripe Connect, internal ledger, etc.). |
| Response | `{ result_for_ledger: { credit_id, ledger_url?: "..." } }` |

| Errors | 422 if amount exceeds a customer-configured ceiling; the response body should include `{ permanent: true, error: 'amount_exceeds_ceiling' }` so substrate doesn't retry |

### Audit projection (in the customer's main app)

After running each handler, the customer's main app should write its OWN audit row (e.g., into their `activities` table) referencing the `action_id`. This is the cross-recipe forensics trail. Sample:

```typescript
await ctx.db.query(
  'INSERT INTO activities (kind, entity_type, entity_id, payload) VALUES ($1, $2, $3, $4)',
  ['support_action_executed', 'customer', payload.customer_substrate_id, { action_id, capability, result }]
);
```

The substrate ledger entry remains the source of truth across recipes — this local row is the in-app trail.

### (B) Signal projection — feeding the deep tier

The agent's deep diagnosis reads:
1. Person/company entities (already populated by the CRM via `ingest-gmail` — no extra work for CRM users).
2. **Product source_artifacts that the customer's main app projects.**
3. Memory (decisions, commitments, learnings).

If the customer doesn't project (B.2), the agent silently falls back to commodity-tier (RAG-only). The deep moat materializes in proportion to what the customer projects. Recommendation per signal kind:

| Signal | Substrate capability | Frequency | Why |
|---|---|---|---|
| **Failed login / auth event** | `upsert_source_artifact` (kind: `failed_auth_event`) | Per-event, debounced (one per minute per user) | Agent sees "this customer hit 3 failed logins in the last hour" when diagnosing a login-related ticket |
| **Failed payment / billing event** | `upsert_source_artifact` (kind: `failed_payment`) | Per-event | Diagnoses upgrade failures, expired cards, etc. |
| **Webhook delivery failure** | `upsert_source_artifact` (kind: `webhook_failure`) | Per-event | Diagnoses integration outages and reproduces retry context |
| **Account state snapshot** | `upsert_entity` (merge into person entity attrs) | On change, OR daily | `plan`, `mrr_usd`, `is_trial`, `trial_ends_at`, `is_disabled`, `feature_flags_overrides` — the agent needs these for both diagnosis context and the disclosure-filter's "what's outbound-safe" determination |
| **Major product action (key feature used)** | `upsert_source_artifact` (kind: `product_event`) | Per-event, sampled | Lets the agent answer "I used X feature yesterday and it didn't work" with real context |

#### Internal-only marking

When projecting account attributes, the customer's main app should mark sensitive fields with the substrate convention `{ ..., _internal_only: true }` on the attribute level, so the support recipe's outbound disclosure filter scopes them away from customer-facing replies. Examples:

```typescript
await ctx.substrate.propose('upsert_entity', {
  type: 'person',
  canonical_keys: { email: '...' },
  attrs: {
    name: 'Jane Doe',
    plan: 'pro',          // outbound-safe
    mrr_usd: 49,           // automatically internal-only via the substrate's MRR field convention
    notes_internal: { value: 'high-risk churn', _internal_only: true },
  },
});
```

The recipe's outbound disclosure filter reads only the outbound-safe subset; the agent's diagnosis path reads everything.

#### What customers SHOULD NOT project

Per substrate-boundaries — also explicit here so customers don't accidentally pollute the substrate:

- Per-page-view / per-click telemetry (use analytics, not substrate).
- Full chat message logs (use your app's own message table).
- API keys, session tokens, password hashes.
- Raw PII not needed for reasoning (full SSN, full card numbers).
- Internal-team-chat messages (if your product has team chat between *your team*).

### Native vs non-native customers

| Tier | Native (Butterbase) customer | Non-native customer |

### Phase ordering rules

- 0 must come before 1. Schema can't be applied without an app.
- 1's stages can be applied in any order EXCEPT `rls` must come after `schema`. AI/RAG/Realtime can interleave.
- 2a must come before 2b. Frontend depends on functions.
- 2c can happen anywhere after 1 (agent spec doesn't depend on functions).
- 3 layers on 2 with NO migrations, NO breaking changes. Customer can enable/disable capabilities at any time post-deploy.
- 4 requires 2 complete (3 optional).
- 5 requires 4 + everything else complete.

### What we deliberately do NOT build for v1

Already enumerated in `01-idea.md` ("Explicitly OUT of v1") and reaffirmed here:
- Customer-facing autonomous mode (autonomy dial CAN be set to `auto_send` in v1, but is NOT the default and is gated behind a confirmation modal).
- Additional inbound channels beyond widget.
- Live action replay.
- Smart multi-human routing (escalation defaults to one configured target).
- Skill test harness.
- Heavy ticketing machinery.
- Vision / file uploads via widget.
- Companion-app skeleton template (deep tier customers self-implement the adapter contract — companion repo is post-v1).
